# Continuum — Phase 6: Memory + Recovery

## Context

Phase 4 and Phase 5 give Continuum a working *single-shot* execution: plan → agent → validate → done. Two capabilities are still missing for long-running, production-grade operation:

1. **Memory** so the system can run for hours without forgetting earlier decisions, and so subsequent sessions benefit from prior work on the same repo.
2. **Recovery** so a crashed or cancelled run can be resumed, replayed, or rolled back without starting over.

Without these, the runtime is effectively stateless and fragile — a system that "executes autonomously for hours" needs both. Phase 6 implements the three-layer memory engine and the checkpoint/replay/stuck-detection machinery on top of `continuum-storage`.

## Recommended approach

### A. Memory engine (`continuum-memory`)

1. **Three-layer model.**
   - **Hot.** Full-fidelity items, capped at N tokens total (configurable, default 64k). Stored in `memory_items_hot` SQLite table, no vector index needed — recall is by recency + tag.
   - **Warm.** Compressed summaries (one summary per ~8 hot items, generated by the memory-agent). Stored in `memory_items_warm`, vector-indexed.
   - **Cold.** Archived warm items past a configurable age. Same table layout as warm but vector index is the only access path.
2. **`MemoryStore` impl.** `LayeredMemory` wraps the existing `continuum-storage` repositories and adds a `Recall` algorithm:
   - First, exact-match on `tags`.
   - Then, vector search against hot+warm+cold concatenated, weighted by tier (hot > warm > cold).
   - Then merge, dedupe, return top-N within `RecallQuery.limit`.
3. **Compression.** `compress(scope)` invokes the **memory-agent** (a new subagent — see below) to summarize hot items in batches. Uses a cheap-tier model. Promoted summaries land in warm; the originals stay in hot until the hot-tier cap evicts them.
4. **Eviction.** Hot tier evicts oldest-first when over budget. Promoted-and-still-hot items are evicted preferentially (their summary exists in warm).
5. **Decision journaling.** Every agent outcome and every plan node completion writes a `MemoryItem` with tag `decision`. Phase 6's main observable: `continuum memory list --tags decision` shows the full session history.

### B. Memory agent (`continuum-agents`)

New subagent: `MemoryAgent` with `kind() == AgentKind::Memory`.
- Triggered by the scheduler (not by user goals) when `Hot tier > 80% of cap`.
- Reads a batch of hot items, asks the cheap model to summarize, writes the summary to warm, returns.
- Runs concurrently with the main scheduler — never blocks task dispatch.

### C. Recovery (`continuum-recovery`)

1. **`RecoveryStore` impl.** `SqliteRecovery` wraps `continuum-storage`'s `checkpoints` and `replay_events` tables.
2. **Checkpoint cadence.** `Scheduler::run` calls `checkpoint(session, state)` after every successful task node. `SessionState` is the runtime's serialized internal state: pending nodes, completed nodes, agent outputs, memory hot-tier snapshot reference, sandbox snapshot ID.
3. **`rollback(to)`** returns the serialized state plus instructions to restore the sandbox to the recorded `SnapshotId`. The CLI verb `continuum rollback <session> <checkpoint>` is wired in this phase.
4. **`replay(session, from)`** streams `ReplayEvent`s. Every span emitted by the runtime via `tracing` is also persisted (via a custom `tracing::Layer` that batches writes to the `replay_events` table) keyed by `SessionId`. Replay just reads them back in order.
5. **Stuck-task detection.** A heartbeat coroutine runs in the scheduler, writing a row to `session_heartbeats` every 30s. `detect_stuck` returns:
   - `StuckReason::NoHeartbeat` if the latest row is older than 5 min.
   - `StuckReason::RetryLoop` if any node has been retried more than 5 times.
   - `StuckReason::BudgetOverrun` if cumulative USD exceeds `ExecutionContract.estimate.usd × 1.5`.

### D. CLI verbs become real

- **`continuum resume [--session ID]`** — loads the most recent (or named) session, calls `RecoveryStore::latest`, restores the sandbox snapshot, resumes the scheduler from the next pending node.
- **`continuum replay <session>`** — streams replay events to stdout, optionally filtered by tracing target.
- **`continuum memory list|compress|purge`** — operates on the live memory store.
- **`continuum doctor`** gains a `--check-stuck` flag that runs `detect_stuck` across recent sessions.

### E. Architectural wiring

- `Session::new` now opens both memory and recovery handles, passes them into `AgentContext`.
- Agents read context via `memory.recall(...)` instead of building prompts from scratch.
- The runtime's tracing layer is the *only* place that writes to `replay_events` — agents and tools never write directly. This keeps replay deterministic.

### Risks and mitigations

- **Replay storage size.** Tracing spans at debug level can be voluminous. Mitigation: per-target filter (only `continuum-runtime`, `continuum-agents`, `continuum-validation` get persisted; deeper internals stay in-memory). Compress on write.
- **Snapshot/state coherence.** Sandbox snapshot ID and `SessionState` must commit atomically. Mitigation: snapshot first; if checkpoint write fails, delete the sandbox snapshot before erroring.
- **Replay clock skew on `time::OffsetDateTime`.** Always use UTC; never serialize timezone offsets.
- **Memory compression cost.** Cheap-tier model only. Budget the compression spend separately so a runaway compress loop is detectable via `BudgetOverrun`.

## Verification

1. **Resume round-trip.** `continuum execute --goal X` interrupted via SIGINT after 2 nodes; `continuum resume` finishes the remaining nodes. Final diff matches a non-interrupted run.
2. **Replay determinism.** Two replays of the same session produce byte-identical event streams.
3. **Stuck detection.** Start a session, kill the runtime non-cleanly; `continuum doctor --check-stuck` reports `NoHeartbeat` for that session.
4. **Memory recall.** Run two sessions on the same repo with related goals; the second session's prompts contain recalled summaries from the first (visible via `tracing` at debug).
5. **Compression budget.** Pump 1000 fake hot items; assert hot tier returns to ≤ cap and warm has new summary items; USD spent on compression is below configured cap.
6. **Storage migration safety.** Apply `0003` then immediately roll back; data from `0001` and `0002` is intact.
